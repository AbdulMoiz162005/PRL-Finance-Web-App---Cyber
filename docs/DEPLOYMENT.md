# Deployment Guide

Production topology:

| Layer     | Host       | Purpose                                        |
|-----------|------------|------------------------------------------------|
| Database  | Supabase   | PostgreSQL: schema, seed, RLS                   |
| Backend   | Render     | Express REST API (SQLite fallback disabled)     |
| Frontend  | Netlify    | React SPA, calls backend via `VITE_API_URL`     |

---

## 1. Supabase — database

1. Create a project at https://supabase.com (keep the region close to your API host).
2. Open the **SQL editor** and run the migrations **in order**:
   - `database/migrations/001_schema.sql` — tables, enums, indexes, `updated_at` triggers
   - `database/migrations/002_rls.sql` — enable RLS + revoke anon/authenticated access
3. No SQL seed is needed in production — the backend seeds demo data when
   `SEED_ON_BOOT=true` (the first time it boots against an empty database).

Credentials you need from **Project Settings → API**:
- `Project URL` (e.g. `https://xxxx.supabase.co`)
- `service_role` key (keep private; it bypasses RLS)

> Security: the backend uses the `service_role` key. RLS policies intentionally
> deny `anon`/`authenticated` access so data can only be read/written through the
> API, where your own role-based access control (JWT) is enforced.

## 2. Render — backend API

### Option A: Blueprint (recommended)

The repository includes `render.yaml`. In the Render dashboard choose
**New → Blueprint** and select this repository. Then fill in the sync-pending
secrets:

| Variable                   | Value                                          |
|----------------------------|------------------------------------------------|
| `SUPABASE_URL`             | Supabase Project URL                           |
| `SUPABASE_SERVICE_ROLE_KEY`| Supabase service_role key                      |
| `CORS_ORIGINS`             | Comma-separated origins, e.g. `https://<app>.netlify.app` |

`JWT_SECRET` is auto-generated by the blueprint. It signs API session tokens
(independent of Supabase auth).

### Option B: Manual web service

- Build command: `cd backend && npm ci && npm run build`
- Start command: `node dist/index.js`
- Add the env vars from `.env.example`:
  `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `USE_SUPABASE=true`,
  `SEED_ON_BOOT=true`, `JWT_SECRET`, `CORS_ORIGINS`, `PORT=10000`

Verify the service is healthy at `GET /health`.

> `SEED_ON_BOOT` is idempotent — safe to leave `true`, but you can set it to
> `false` after the first successful boot to guarantee no demo data is created.

## 3. Netlify — frontend

1. Import the repository in Netlify (**Add new site → Import an existing project**).
   `netlify.toml` already sets build command, publish directory and SPA redirects.
2. Set the build-time environment variable:
   - `VITE_API_URL=https://<your-render-service>.onrender.com`
   (no trailing `/api` — the app appends `/api/...`).
3. Deploy. The site is served at `https://<app>.netlify.app`.

### Local development

```bash
# backend
cd backend && npm install && npm run dev        # :3001

# frontend (no env vars needed; /api is proxied to :3001)
cd frontend && npm install && npm run dev        # :5173
```

## 6. Production notes

- **Backups**: Supabase runs continuous backups automatically; check your plan's
  PITR settings under Database → Backups.
- **Secrets**: never commit `SUPABASE_SERVICE_ROLE_KEY` or `JWT_SECRET`. Use the
  platform secret managers (Render env vars, Netlify env vars).
- **CORS**: `CORS_ORIGINS` must include your exact Netlify origin. Multiple origins
  are comma separated.
- **Health checks**: Render health check path `/health` is used to mark the
  service live.
